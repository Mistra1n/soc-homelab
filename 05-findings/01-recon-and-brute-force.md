# Incident report: Reconnaissance and RDP brute force against win-victim

## Summary

Two simulated attacks were run from `kali (192.168.56.30)` against `win-victim (192.168.56.20)`: an nmap port scan, and an RDP password brute force with Hydra. The scan produced no SIEM alert at all — a genuine visibility gap. The brute force was fully caught, first by Wazuh's default ruleset and then earlier by a custom rule written for this lab. Together they show both what the current setup can and cannot see.

## Detection

- **Port scan (T1046):** No rule fired. Sysmon and the Wazuh agent log host-level activity (processes, files, registry); a SYN scan against filtered ports never touches a process on the host, so there was nothing for the agent to see. No network-layer IDS (Suricata/Zeek) is present in this lab to catch it at the wire.
- **RDP brute force (T1110.001):** Caught twice —
  1. Wazuh's **built-in** rule `92657` flagged the successful logon itself, with an automatic NTLM/pass-the-hash/RDP heuristic in its description.
  2. A **custom** rule (`100001`, see [`04-detection-rules/`](../04-detection-rules/)) flags 5+ failed logons from one source within 2 minutes, and fired *before* the successful logon — giving a defender warning during the attempt rather than only after.

## Analysis

- **Attacker behavior:** reconnaissance (T1046) followed by credential brute forcing (T1110.001) against a single exposed service (RDP, port 3389) — a realistic, minimal attack chain.
- **Affected host:** `win-victim` only; the attack stayed within the isolated `VMnet2` lab network throughout (see [`01-setup/`](../01-setup/) for isolation verification).
- **Why the scan was invisible:** host-based agents (Sysmon + Wazuh) see what happens *on* the endpoint. A scan that never completes a connection to anything leaves no process, file, or logon trace — it needs to be seen on the wire instead.
- **Why the brute force was visible:** it completed real Windows authentication events (failed and successful logons), which are exactly what host-based Security-log monitoring is built to catch.

## Response

No real response actions were needed (simulated attack, isolated lab, both machines are my own). In a real environment, the response to the brute force would be: disable or lock the targeted account, block the source IP, and review whether the account's privileges (flagged via `67028`, "special privileges assigned to new logon") were used for anything after the logon.

## Recommendations

1. **Close the scan visibility gap.** Add either Windows Firewall log collection (cheap: ship `pfirewall.log` as a Wazuh log source) or a network IDS (Suricata on the VMnet2 span) so reconnaissance is visible, not just completed attacks.
2. **Keep the custom rule, but know its limits.** `100001` is tuned to this lab's attack speed (`frequency=5, timeframe=120`). A slower, "low and slow" brute force spread over hours would not trip it — worth a second, longer-window rule if this lab continues.
3. **NLA matters.** This lab disabled RDP's Network Level Authentication requirement so Hydra's module could complete the handshake at all. In practice, NLA is a real mitigation against this exact attack pattern — re-enabling it should be the default recommendation for any real RDP-exposed host.
4. **Snapshot discipline.** Take VM snapshots immediately after confirming and screenshotting new evidence, not only as a single "clean" baseline — a revert during this project erased one full attack's evidence before it was written up (see [`03-attack-simulations/README.md`](../03-attack-simulations/README.md)).
